# Stage 0 — Establish the project and resume safely

Use the visible conversation, existing files and project state.json before asking for
information. A new session may already have everything needed. Read
references/model.md and references/evidence-contract.md before substantial drafting.

## Resolve the inputs

| Input | How to use it |
|---|---|
| Destination, audience and purpose | Recover from the request or project; clarify only an ambiguity that materially changes the work |
| Corpus export or site content | Use for voice, topics and existing coverage; research consequential facts with current primary sources |
| Existing title and product scope | Preserve accepted choices; do not restart naming or planning merely because the session changed |
| Brand tokens or site styles | Read the project's tokens or derive a reasonable draft palette and typography from available assets |
| Previous build | Use to resume the same project, then inspect actual sources and outputs |
| Price, formats and update promise | Honor what is known; do not invent a price, sales claim or ongoing maintenance service |

An absent export, stylesheet or article quota does not automatically block useful work.
Inspect accessible project material, prepare an outline and identify specific gaps. When
an unavailable input makes a reliable claim or essential design match impossible, limit
that part of the draft and say what is missing. Ask for information the user uniquely
holds only when it matters and cannot reasonably be inferred or retrieved.

## Opening sequence

1. Read the project's existing state.json, if present. Confirm destination, stage,
   outputs, outstanding work and prior decisions against the actual files.
2. Identify the corpus, previous build, brand assets and existing evidence record. Read
   any topic plans as hypotheses rather than instructions to invent support.
3. Start Stage A's coverage and verification plan. Use the corpus as editorial input;
   maintain evidence.json for verified claims, uncertainty and shared rules.
4. Read project brand tokens or derive a reversible visual direction from available
   assets. Show a useful sample when it helps review; do not impose an approval gate for
   routine styling or a title the user has already supplied.
5. Record material assumptions and continue the work authorized by the request. Reserve
   clarification for an irreducible scope choice, not every implementation preference.

Reuse tools, components and editorial methods across projects. Recheck destination facts,
coordinates, rights, assets and recommendations. Another destination's manuscript is not
a verified starting point with interchangeable names.

## Resuming a build

Inspect an archive's contents before extracting it into a project-specific directory.
Read its sources and build entry point; do not assume that a file called final is current.
Verify the selected build actually updates its outputs before trusting a previous PDF.

Keep build paths portable. Use the available runtime and installed render dependencies;
do not assume a browser exists at a path copied from another environment. Follow the
project's documented commands and inspect errors rather than silently reusing a stale
render.

Review the existing evidence dates, critical rules, planned images and unresolved notes.
An inherited image may be a placeholder. Establish its provenance and intended use; never
present generated or unverified material as first-hand field documentation. Revalidate
affected sections and artifacts after substantive changes, with visual review of the
finished export.

## Handover

Update project state with the current stage, source and output locations, revision dates,
decisions made and material open issues. Preserve the source build and evidence record
with the deliverables according to the workspace's saving rules. Package the build when
needed for portability or requested by the user; do not add redundant archives by habit.

Report what is finished, what was checked and any limitation that affects use. Page and
word counts may describe the output; they do not certify its quality. Do not claim that
an image, factual check, live site update or scheduled refresh is complete unless it is.
